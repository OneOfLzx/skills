# Clarify Requirements

当你在执行任务时遇到**疑问/描述不清晰/关键约束缺失/多条可选方向需要用户选择/验收标准不明确**，必须先用一次“交互式澄清”把不确定性消掉，再继续后续实现。

## 触发条件（任意满足即可）

- 需求语句存在歧义：同一句话可解释为多种行为
- 关键约束缺失：平台/版本/兼容性/性能/安全/数据规模/接口契约
- 有多条合理实现方向，需要用户偏好或取舍（复杂度 vs 风险 vs 速度）
- 缺少可验证的验收标准
- 需要用户提供外部信息：环境、权限、样例输入输出、现网现象细节

## 交互式澄清的默认流程

### 1. 优先：使用当前工具内置的“提问”能力

选择最贴近问题的交互类型：

- **单选**：路线选择（推荐，能减少歧义）
- **多选**：同时选择多个约束/偏好
- **单行文本**：开放式回答

要求：

- 提示语必须自洽、可独立理解，不引用“如上/同前”
- 如果是路线选择，选项必须互斥且覆盖主要分支，并给出“我推荐的默认项”

拿到用户答案后，继续生成后续内容。

### 2. 兜底：使用阻塞式 CLI 脚本（跨环境）

当你无法使用内置交互 UI（或不确定是否可用）时，使用脚本进行**真正阻塞**的问答。

命令（Windows / macOS / Linux 通用）：

```bash
python scripts/clarify-requirements.py --question "把你希望我采用的方案写清楚（例如 A/B/C）"
```

脚本会：

- 在终端显示问题
- **阻塞等待**用户输入
- 输出仅包含答案的 JSON（标准输出）

你必须把脚本的 JSON 输出作为“答案”继续后续工作，不要让日志污染输出解析。

NOTE: 脚本一次传递一个问题给到用户，如果你有多个问题需要询问，则需要多次调用脚本。

## 输出约定（脚本）

脚本输出（stdout）严格为：

```json
{ "answer": "..." }
```

失败时（stderr）打印错误信息，并以非 0 退出码退出。
